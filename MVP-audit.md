Подход «сейчас только заложить, не реализовывать» — правильный для MVP. Ниже — как это стыкуется с тем, что уже есть, и что важно не перепутать.

Главное: в проекте уже есть QR, но не для входа

Сейчас QR — это гостевые пропуска (apps/access): код пропуска, скан на ресепшн, POST /access/validate/, лог с method: 'qr' | 'manual'.

Вход сотрудника в платформу — только email + пароль + JWT. Отдельного flow «QR → логин в мобильное приложение», биометрии и NFC для auth нет.

Сценарий

Статус

QR гостевого пропуска (физический доступ)

Реализован

QR / NFC / биометрия как способ логина

Не реализован, в scope — «на будущее»

Если в ТЗ не разделить эти два QR, заказчик и разработка легко решат, что «QR уже есть» — это разные продуктовые истории.

Почему «только заложить» — разумно

Нет мобильного приложения в репозитории — QR-login без клиента всё равно не проверить end-to-end.

Биометрия и NFC — в основном нативный слой (Keychain, Secure Enclave, HCE). Бэкенд обычно получает уже готовый токен/подпись, а не «отпечаток».

Безопасность: pairing QR, одноразовые challenge, привязка устройства, отзыв — отдельный дизайн; половинчатая реализация хуже, чем явный «не в MVP».

JWT + httpOnly refresh уже нормальная база для любого будущего канала: новый способ входа = новый endpoint, который в конце выдаёт те же access + refresh cookie.

Полная реализация сейчас — дорого и рискованно; архитектурный задел — да.

Что разумно считать «заложить» (минимум, без UI)

Достаточно документа + мелких расширяемых точек, без экранов «Войти по QR»:

ADR / раздел в auth-доке — три канала отдельно:

QR login (web показывает challenge → mobile сканирует → обмен на JWT),

биометрия (локальная разблокировка уже выданного refresh на устройстве),

NFC (пропуск/турникет vs login — разные интеграции, как в MVP §5.3).

Расширяемый AccessLog.method — сейчас только qr и manual; при миграции можно зарезервировать nfc, biometric (или generic external), без логики.

Не трогать GuestPass.qr_code под логин — отдельная сущность/таблица вроде AuthChallenge / DeviceCredential, когда дойдёте до реализации.

OpenAPI: тег Auth (future) с заглушками 501 — опционально; часто хватает описания в schema без эндпоинтов.

Не стоит «закладывать» сейчас: половина UI на логине, фейковые кнопки «Войти по NFC», неиспользуемые таблицы без ТЗ — это техдолг без пользы.

Как это связано с «Запомнить меня» и idle

QR-login в мобилке после успеха всё равно сводится к выдаче JWT — те же правила remember_me, refresh TTL, blacklist при смене пароля.

Биометрия на телефоне чаще = «разблокировать уже сохранённую сессию», а не отдельный тип пользователя на бэкенде.

Idle timeout (когда появится) — на клиенте; к QR/NFC на сервере почти не привязан.

То есть будущие каналы наследуют текущую модель сессии, а не заменяют её.
